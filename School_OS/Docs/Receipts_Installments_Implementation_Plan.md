# Receipts & Installment Payments — Implementation Plan

**Status:** Proposed  
**Owner:** School OS core  
**Target:** Teacher-approved requirement — receipt printed the moment a payment is recorded (cash or online), fee collection in installments, and a permanent downloadable/printable receipt copy on the parent portal.

---

## 1. What the current system already gives us (don't rebuild)

The architecture already supports most of the heavy lifting. The plan builds on it rather than replacing it.

| Capability | Where it lives today |
| :--- | :--- |
| **Invoice ledger** | `StudentInvoice` — `invoice_number`, `total_amount`, `amount_paid`, `balance`, `status` (`draft/unpaid/partial/paid/cancelled`) |
| **Per-payment records** | `PaymentTransaction` — auto-unique `receipt_number` (`RCT-XXXXXXXX`), `amount`, `payment_date`, `method` (`cash/bank/momo/cheque`), `reference`, `recorded_by`, `notes` |
| **Partial / installment payments** | Already works: any amount ≤ balance is accepted and flips invoice to `partial`. Both admin and parent paths allow it. |
| **Receipt PDF engine** | `finance/utils.py` — ReportLab A4 print-friendly PDF, school header/address/contact, line items, totals |
| **Payment notifications** | `notify_payment_received` — parents + admins get a notification titled with the receipt number |
| **Tenant branding** | `Tenant.theme_config` (primaryColor), `logo_url`, `motto`, `address`, `phone`, `email`; `TenantConfig.currency_symbol`, `payment_methods` |
| **Tenant isolation** | `BaseTenantViewSet` + `request.tenant` middleware + `ParentStudentRelationship` scoping (reused across all parent views) |

### The core problem
The existing receipt PDF is **invoice-level** and reads `invoice.transactions.first()`. Because transactions are ordered newest-first, every receipt prints the *same* invoice balance picture and only the most recent payment's method/reference. For an installment flow that is misleading and wrong. Also, **parents have no endpoint** to download any receipt, and **no print flow** exists in either portal.

---

## 2. Goals (teacher's asks → deliverables)

1. **Receipt immediately after payment is recorded** — cash (admin/bursar) and online (parent).
2. **Fees collectible in installments** — each installment gets its own receipt with correct running balance.
3. **Receipts printable** — from school office and parent portal, at any time, without trouble.
4. **Parent portal copy** — permanent archive of every receipt, downloadable + printable on demand.

### Design principle
**A receipt is a faithful, deterministic rendering of an immutable `PaymentTransaction`.** Receipts are generated on demand from transaction data — no PDF storage, no drift, nothing to manage. If the same receipt is opened in a year it prints identically.

## 3. Backend design

### 3.1 Two receipt types (one engine, two templates)

**Type A — Payment Receipt** (the deliverable). One per `PaymentTransaction`. What the office hands over and parents download.

- School header (branded: logo, name, motto, address, phone, email, primary-color rule)
- "OFFICIAL RECEIPT" + `Receipt No: RCT-…`
- Payment date, method, gateway/bank reference, recorded-by
- Student name, admission number, class, academic year
- Invoice number it settles
- **This installment amount** (prominent)
- **Running balance after this payment** + cumulative paid so far
- Verification code / QR (see 3.4)
- Signature line + "Generated by School OS on …" footer

**Type B — Fee Statement** (invoice summary). The payment-history ledger for one invoice.

- Same branded header
- Invoice number, student, class, academic year, due date, total
- **Table of every installment**: date, receipt no, method, reference, amount, running balance
- Total billed / total paid / outstanding balance

### 3.2 New + updated endpoints

| Method & Path | Access | Purpose |
| :--- | :--- | :--- |
| `GET /finance/transactions/{pk}/receipt/` | Admin/Bursar | Print a single payment receipt (Type A). `Content-Disposition: inline` so the browser shows/prints. |
| `GET /finance/invoices/{pk}/statement/` | Admin/Bursar | Print fee statement (Type B). *Replaces* the old `…/receipt/` on invoices (which becomes `…/statement/`). |
| `GET /students/parent-receipts/` | Parent | List every receipt (transaction) across linked wards with `receipt_number`, amount, date, method, invoice, student, status, download/print URL. |
| `GET /students/parent-receipts/download/{transaction_id}/` | Parent | Return Type A PDF for one transaction. Authorization: transaction must belong to a student linked to the caller. |
| `GET /students/parent-receipts/statement/{invoice_id}/` | Parent | Return Type B statement PDF for one of their invoices. |
| `GET /finance/receipts/verify/{receipt_number}/` | Public (rate-limited) | Masked authenticity lookup: school, student initial, amount, date, "valid" flag. Lets a bank/employer confirm a paper receipt. |
| `POST /students/parent-payment/` | Parent | **Update response** to include `transaction_id` + `receipt_url` so the success screen can auto-open the receipt. |
| `POST /finance/transactions/` | Admin/Bursar | **Update serializer response** with `receipt_url` + `balance_after`. |

**Cleanup:** delete the redundant `POST /finance/payments/initiate/` (`initiate_payment` in `finance/views.py`) — the frontend uses only `/students/parent-payment/`. Keeps one code path.

### 3.3 Running balance — the installment correctness fix

Two options. Recommended: **snapshot column** for audit-grade robustness.

- Add `amount_paid_after` (Decimal) to `PaymentTransaction` — the invoice's cumulative paid *after* this transaction.
- Populate it in every creation path: `PaymentTransactionSerializer.create`, `ParentPaymentView`, and (if kept) `initiate_payment`.
- Backfill command: for each invoice, order transactions by `(payment_date, created id)` and write cumulative totals.
- Receipt prints `amount_paid_after` and derives `balance_after = total_amount - amount_paid_after`.

*Fallback (no migration):* compute cumulative paid in SQL from the ordered immutable transactions. Viable, but fragile if an invoice is ever manually adjusted. The column is cheap and self-documenting.

### 3.4 Verification (cheap credibility win)

- Deterministic verification code = `HMAC(receipt_number, secret)` (short, e.g. 8 digits) printed on each receipt; the public verify endpoint recomputes and masks the student name (first initial + last name), showing amount/date/method. No login, no data leak beyond what's on the paper anyway.

### 3.5 PDF engine refactor (`finance/utils.py`)

- Extract shared helpers: `_branded_header(canvas, tenant)`, `_styles(tenant_primary_color)`, `_money(n)` using `TenantConfig.currency_symbol`.
- `generate_payment_receipt_pdf(payment)` (new, Type A)
- `generate_invoice_statement_pdf(invoice)` (refactor of existing, Type B)
- Keep ReportLab (already a dependency), A4, single page, print margins.
- Brand-adaptive: primary color bar, logo when `tenant.logo_url` exists (fallback to plain text header).

### 3.6 Notifications

- `notify_payment_received`: link becomes `/parent/receipts` (or `/parent/fees?receipt=<tx_id>`), body already carries the receipt number — keep. Optionally append the receipt URL so parents can tap straight to the PDF.

## 4. Frontend design

### 4.1 Shared PDF plumbing
- `src/utils/download.ts` — `downloadBlob(res, filename)` + `openPdf(url)` (new tab → browser print).
- `parentApi.ts` — `getReceipts()`, `downloadReceipt(txId)`, `getStatement(invoiceId)` using `responseType: 'blob'`.
- Admin `api` calls in pages for the two new admin endpoints.

### 4.2 Admin / bursar portal

1. **`RecordTransactionPage.tsx`** — after a successful cash/bank payment: show a **"Print Receipt" success screen** with the receipt number, a *Print* button (opens the Type A PDF in a new tab / auto-`window.print()`), and a *Done* button. No more "navigate away + toast".
2. **`StudentLedger.tsx`** — under each selected student's invoices, add a **transactions panel**: rows of `receipt_no · date · method · amount · balance-after` with a print icon per row (Type A) and a *Statement* button per invoice (Type B).
3. **`FinanceTreasury.tsx`** — add a **"Receipts" / transactions tab** listing all `PaymentTransaction`s with quick print buttons and a search box (receipt no, student). (Reuses the admin list endpoint already available via `GET /finance/transactions/`.)
4. **`InvoiceManagement.tsx`** — add a *Statement* (Type B) print button on each invoice row.

### 4.3 Parent portal

1. **`ParentFees.tsx`**:
   - Invoice cards for `partial`/`paid` invoices get **"Receipts"** and **"Statement"** buttons → open a receipt archive for that invoice.
   - Payment success screen: immediately show **"Download Receipt"** + **"Print Receipt"** (auto-fetch `receipt_url` from the payment response).
   - Installment copy under the amount field: *"You can pay in installments. Enter any amount up to the balance — each payment gets its own receipt."*
   - After an installment, the invoice card refreshes to show `x of y paid · remaining …` and the new receipt appears instantly in the archive.
2. **New `ParentReceipts.tsx`** page + route `/parent/receipts` (add to `ParentLayout` nav) — a clean **receipt archive**: grouped by child, each row shows receipt no, date, amount, method, invoice; *Download* and *Print* buttons. Empty state with instructions. This is the "copy they can download and print at any time."
3. **`ParentDashboard.tsx`** — "Pay Fees" quick action stays; payment-alert tap routes to `/parent/fees?receipt=<tx>` when present.

### 4.4 Installment UX summary
- Enter amount ≤ balance (already allowed both sides) → each successful payment mints its own immutable receipt → running balance printed → parent archive + admin ledger both update. Explicit installment copy + per-receipt actions make the flow obvious instead of accidental.

## 5. Security & audit

- **Tenant isolation:** every new queryset filters by `request.tenant` (existing `BaseTenantViewSet` pattern) or by `ParentStudentRelationship` for parent endpoints.
- **Parent scope:** `parent-receipts` endpoints verify `ParentStudentRelationship(parent_user=request.user, student=…)` exactly like `ParentFeesView` / `ParentPaymentView`.
- **Immutability:** transactions are never editable/deletable (`allow_delete=False`, serializer read-only) → receipts are permanent by construction.
- **Public verify endpoint:** masked output only + rate limiting.
- **No new secrets exposed:** verification HMAC uses the Django `SECRET_KEY`; never printed/logged.
- **Audit:** keep `recorded_by` (already captured). Optionally log receipt generations in the existing `audit` app.

## 6. Data / migrations

- `PaymentTransaction.amount_paid_after` — one migration (nullable initially) + a backfill management command (`backfill_payment_balances`).
- No new models. No PDF storage. No new tables.
- `TenantConfig` unchanged (currency symbol already present).

## 7. Testing / QA

- **Unit (backend):** receipt generator returns valid PDF (PyPDF/text sniff for header + receipt no); running-balance math for 3-installment scenario; over-payment rejected; parent endpoint 403 for a non-linked student; verify endpoint returns masked data.
- **API tests:** each new endpoint with correct/incorrect tenant + role.
- **Frontend (manual checklist):**
  - Cash payment recorded by bursar → print receipt opens, prints correct installment + balance.
  - Parent pays 40% → receipt 1 shows balance-after; pays remaining 60% → receipt 2 shows zero balance; invoice flips to paid.
  - Parent archive shows both receipts; download + print work; PDF persists across re-login.
  - Public verify link on a printed receipt works and shows masked data.
- **Regression:** fee generation, reminders, expense flow, existing parent analytics/reports unaffected.

## 10. Open questions (confirm before build)

1. **Receipt numbering:** keep the existing random `RCT-XXXXXXXX`, or switch to a sequential per-school series (e.g. `2026-000123`) that looks better on paper and is easier to verify? (Sequential needs a per-tenant counter — small extra work.)
2. **Minimum installment:** any amount down to 1 XAF is currently allowed. Want a school-configurable minimum installment (e.g. 10% of balance)?
3. **Verification:** include the public HMAC verify step in v1, or ship it as phase-4 polish?
4. **Receipt copy for a cancelled/voided invoice:** print a void note or nothing?
5. **FR/EN:** receipts should render labels in the tenant's `default_language` (some strings exist in EN only today). Confirm we translate receipt labels in v1.
